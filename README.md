# Prompt Generator для тестовой документации

Система на Python 3, которая принимает требования и генерирует промпт для LLM,
а затем прогоняет его через локальный Ollama и оценивает качество.

## Что генерируется

На выходе LLM получаются четыре артефакта:
1. **Test Plan** — цель, объект, стратегия, критерии входа/выхода, окружение, риски.
2. **Checklist** — краткий чек-лист проверок.
3. **Test Cases** — таблица тест-кейсов + таблица трассируемости к требованиям.
4. **QA Report** — сводка прогона: пройдено/провалено, дефекты со ссылками на TC.

## Требования

- Python 3.10+
- Docker + образ `ollama/ollama`
- Модель `qwen2.5:7b` (скачивается через `ollama pull`)

## Запуск

### 1. Поднять Ollama в Docker

```bash
docker run -d -v ollama:/root/.ollama -p 11434:11434 --name ollama ollama/ollama
2. Скачать модель
bash
docker exec -it ollama ollama pull qwen2.5:7b
3. Создать venv и установить зависимости
bash
python -m venv .venv
.venv\Scripts\activate.bat      # Windows cmd
pip install -r requirements.txt
4. Запустить прогон
bash
python test_prompt.py
Скрипт:

генерирует промпт из требований (редактируются в test_prompt.py, константа REQUIREMENTS);

проверяет доступность Ollama и модели;

отправляет промпт в LLM;

сохраняет промпт и ответ в results/ с timestamp в имени.

Время выполнения на CPU без GPU — от 1 до 10 минут.

Входные требования (пример)
Функциональность «Корзина интернет-магазина» — 8 пунктов, включая добавление товара,
изменение количества 1–10, удаление, пересчёт стоимости, обработку отсутствия на складе,
лимит 20 уникальных товаров. Полный текст — в test_prompt.py.

Результаты тестирования и оценка качества
Тестирование проводилось через Ollama (qwen2.5:7b) в два прогона:

v1 — базовый промпт.

v2 — промпт с явными требованиями к покрытию, трассируемости и унификации приоритетов.

Оценка по критериям (1–5)
Критерий	v1	v2	Комментарий
Читаемость	5	5	Структура, markdown и порядок разделов соблюдены в обеих версиях.
Контекстность	4	5	v2 покрывает все 8 требований через трассируемость; v1 пропускал 2–3 требования.
Чёткость целей	4	5	В v2 задан измеримый минимум (8 кейсов, типы, обязательные сценарии). Модель его выполнила.
Покрытие сценариев	3	4	v2 включает все позитивные/негативные/граничные кейсы; минус балл за нелогичную трассируемость в 2 строках и пропуск лимита 20 в checklist.
Средний балл	4.00	4.75	
Выводы
Базовый промпт (v1) даёт рабочую, но неполную документацию: модель «проскакивает» часть требований, если явно не указать, что нужно покрыть все.

Ключевые улучшения v2, давшие прирост:

Явное требование покрытия каждого требования + таблица трассируемости — устраняет пробелы.
Перечисление обязательных тест-кейсов — гарантирует нужные сценарии.
Унификация приоритетов — устраняет разнобой П/P/N.
Запрет «выдуманных» дефектов — QA Report ссылается на конкретные TC-ID.
Остаточные слабости v2 (некритичные): checklist не сгруппирован по модулям, трассируемость для требований 2 и 8 семантически неточна. Это можно устранить в v3, но для сдачи достаточно.
